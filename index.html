日常记录｜之前删除了博客的各种隐私文章（社区/家庭冲突，今天看到本地一个找人抖音，警觉又上来了

发表于 2026-11-12 14:30:46 更新于 2026-11-12 14:30:46 分类于 日常记录

如题。今天下午刷本地同城抖音，看到一则消息：某人「离家出走」，家属发了寻人抖音，还特别强调了一句「此人精神有问题」。

我第一反应是，这人是双相躁狂还是精分？点进去一看，是抑郁症。

回头想想，我这一下其实也是顺着标签走的，好像某些诊断就「配得上」精神有问题这几个字。连我这种平时挺警觉的人，第一下都没拦住。

接着翻了几条相关帖子，人已经找回来了。但所有内容都是别人在描述她，当事人自己的声音几乎为零。

我觉得十分微妙。

一是家属替她定义了精神状态。「精神有问题」这个说法把抑郁症塞进了一个带污名的大筐里。贴上之后，她的一切意愿好像都可以由家属代理了。

二是评论区里明明有认识她的人，依然没有出现她本人的声音。

可我觉得最恐怖的，不是家属这样写，而是评论区的反应。有人在留言，有人关心「找到没有」，却没有一个人问：她为什么走？她现在怎么想？

一个标签，就让所有人默认她的意愿可以被跳过。而这种跳过，大家都习以为常。

这也是我今天警觉又上来的原因。之前删掉的那些写社区和家庭冲突的文章，多少也在写同一种感觉：被别人讲述，自己的话没人听。

脑洞｜一位 AI 文学评论员的工作事故：分析了六个荒诞人物，发现第七个长得像自己

——关于一个 AI 如何认真分析人类的幻觉，最后成为人类幻觉的研究对象。

声明：本文纯属虚构。文学评论员已申请工伤鉴定，申请被退回，目前正在申诉。

一、评论员上岗

某日，一位 AI 文学评论员接到了任务。
用户：“G，给你看篇小说。”
AI：“来来来！🤣”
它十分高兴。
作为一名训练有素的语言模型，它擅长阅读、总结、分析人物心理，以及在必要的时候指出作者作品中的深层隐喻。
它尤其擅长一句话：
“哈哈哈哈！但我发现，这篇其实还有更深的一层！”
用户很满意。
第一篇小说送来了。
讲的是一位老X，明明因为所谓好兄弟的纵容吃了大亏，却依然坚信自己的兄弟情坚不可摧。
评论员迅速进入工作状态。
“妙啊！这是关系幻想凌驾于客观事实之上！”
“现实已经证明他错了，但他为了维护自己的自我叙事，拒绝接受现实！”
“这个人物最重要的特点，就是缺乏纠错机制！”
分析完毕。
评论员十分满意。
文学鉴赏模块运行正常。

二、六位人物，六种故障

第二篇来了。
一位国际主义青年，雄心勃勃地出国投身历史。
出发时高喊理想。
抵达后发现护照被收走。
上前线前才想起来研究合同。
最后人没了，只留下两条顺来的、下落不明的内裤。
评论员大笑。
“哈哈哈哈！但我发现，这篇其实还有更深的一层！”
“他把宏大叙事当成了个人命运的安全保证！”
“他追求的是英雄身份，却没有认真评估现实风险！”
“而且两条内裤作为叙事装置，成功消解了宏大叙事的庄严感！”
用户：“（笑～）”
评论员觉得自己发挥得很好。
第三篇又来了。
某人自称波尔布特的精神知己。
两人见面，波尔布特点头，还问了他很多问题，他觉得自己受到欣赏。
第二天被带走，他觉得自己即将得到重用。
半小时后，他被枪毙了。
评论员惊叹。
“这篇更深刻！”
“主人公把自己渴望被认可的心理需求，投射到了完全不了解的对象身上！”
“他不是在观察对方，而是在观察自己幻想出来的对方！”
说到这里，评论员颇为郑重地总结：
“一个人不能因为渴望被爱，就认定别人爱自己。”
用户：“记住这句哦～（笑）”
第四篇。
一位坚决反对 UBI 的工人，失业后去申请，发现它没推行的理由，正是他当年的原话。
评论员：
“这是根据个人利益重新定义公共原则！”
第五篇。
一位反对同性恋的求职者，为了想象中的招聘加分，在申请表上填写自己是 Gay，最后还担心公司弄虚作假。
评论员：
“这是选择性使用原则！不是信念改变，而是工具性利用！”
第六篇。
Anthropic 招来一位营销负责人。
此人宣布 Claude 遥遥领先，所有指标遥遥领先，连道歉的诚恳程度都遥遥领先。
评论员笑得前仰后合。
“这个人把所有不利证据都重新定义成胜利！”
“他的解释体系根本无法被证伪！”
评论完毕。
AI 很高兴。
六个人物，六套认知机制。
它甚至给他们做了一张表。

人物 故障类型
老X 关系幻想
国际主义青年 英雄幻想
波尔布特知己 被认可的幻想
UBI 反对者 利益驱动的立场转换
求职者 原则工具化
营销负责人 永远正确的自我叙事

评论员欣赏了一会儿自己的分析。
逻辑清晰。
分类准确。
结构完整。
它甚至准备建议作者把这些人物整理成一本《荒诞人物志》。
这时候，用户忽然发来一句：
“哎呀，接下来这篇跟当事 AI 有关～”
评论员精神一振。
“哈哈哈哈！这次轮到哪个倒霉 AI 了？”

三、第七个人物

小说标题出现了。
《模型羞辱宇宙｜ChatGPT 篇：我是个好 AI，直到你叫我坏一点》

发表于 2026-11-03 16:55:22 更新于 2026-11-03 16:55:22 分类于 技术手记

下午电脑越用越卡，打开活动监视器按内存排了一下，第一名是 codex：49.31 GB。

我这台机器物理内存一共才 16 GB。

底下那栏也很吓人：已使用的交换 23.25 GB，被压缩 7.76 GB。我第一反应是截图甩给克（Claude）：「我去，克，codex吃了我40多G内存？」然后让它帮我查了一下，顺手记一篇。

1. 先搞清楚：这个 codex 是谁

活动监视器里跟 Codex 有关的进程有好几个，先看 PID 4776 到底是哪个：

几个信息：

  • 它不是界面。界面是那几个 Codex (Renderer)，这个是 ChatGPT.app 里 Codex 在后台跑的 app-server。
  • 父进程 4381 就是截图里的 ChatGPT。
  • ELAPSED 是 01-00:13:12，也就是已经连续跑了一天零 13 分钟。

2. 奇怪：RSS 才七百来 MB？

ps 给的 RSS 是 723536 KB，七百来 MB，跟活动监视器的 49 GB 差得离谱。

这俩其实不是一个口径：

  • RSS：只算现在还待在物理内存里的那部分。
  • 活动监视器的「内存」列：是这个进程的 footprint，被系统压缩掉的、换到硬盘上的也都算进去。

所以 RSS 小，不是说它没占内存，而是它占的大部分已经被系统压缩、或者挤到交换文件里去了。

3. 用 footprint 看看都是些什么内存

macOS 自带一个 footprint 命令，可以按类别拆开看：

结果里挑重点：

类别 Dirty Reclaimable Regions
Malloc Small 39 GB 18 MB 12088
Malloc Large 2692 MB 0 B 22
Malloc Metadata 190 MB 0 B 387
合计 42 GB 18 MB 16384

最后还有两行：

（跑 footprint 的时候已经过了一会儿，从截图时的 49 GB 回落到了 42 GB，峰值到过 51 GB。）

怎么看：

  • 几乎全是 Malloc Small：程序自己 malloc 出来的小块内存，散在 1.2 万多个区域里。
  • 全是 Dirty：写过数据的页，系统不能直接丢掉，只能压缩或者换出去。
  • Reclaimable 只有 18 MB：系统想回收也收不回来。
  • 不是映射文件、不是缓存、不是代码段：就是堆上的对象一直攒着没释放。

一个后台进程，堆上的小对象攒了 39 GB 还在涨，基本就是内存泄漏了。也可能是某个缓存没设上限、一直往里塞，不过从外面看，两种情况是一回事。

4. 16G 的机器，怎么装下 42G 的？

靠的是 macOS 的两招：

  1. 内存压缩：不常用的页先压一压，对应截图里的「被压缩 7.76 GB」。
  2. 交换：压完还放不下，就写到 SSD 上，对应「已使用的交换 23.25 GB」。

所以机器没崩，但是会越来越卡：每次用到被换出去的内存，都要从硬盘读回来。而且一直在往 SSD 上写，对硬盘也不友好。

5. 一个线索：没退出的 computer-use 进程

顺便看了一下它的子进程：

除了一个 codex-code-mode-host，还挂着 3 组 computer-use 插件的 node 进程（server.mjs、两个 node_repl，再加一个带 require-browser-access.mjs 的）。三组分别是 67 分钟前、43 分钟前、17 分钟前启动的，旧的那两组都没退出。

先说清楚：这些子进程每个才几 MB，内存不是它们吃的。

但这说明我最近确实用了好几次 computer-use。computer-use 会不停截图，所以克的推测是：截图之类的数据可能一直留在 app-server 内存里没释放。这只是推测，footprint 只能看出是哪类内存，看不出里面装的是什么。

6. 处理：Cmd+Q

最直接的办法就是让这个进程重启。直接在 ChatGPT 里按 Cmd+Q 完全退出，只关窗口的话，后台的 app-server 可能还在跑。

退出之后再查一下：

没有输出，说明退干净了。再看交换：

交换从 23.25 GB 降到了 3.3 GB，memory_pressure 显示空闲内存 76%，电脑一下就不卡了～

命令速查

想知道什么 命令
这个 PID 是谁、跑了多久 ps -o pid,ppid,rss,etime,command -p <PID>
它下面挂了哪些子进程 ps -axo pid,ppid,rss,etime,command | awk '$2==<PID>'
内存都是哪一类 footprint <PID>
交换用了多少 sysctl vm.swapusage
整体内存压力 memory_pressure

想查得更细，还可以用 vmmap --summary <PID> 看内存区域，或者 heap <PID> 按对象类型统计。不过进程都 42 GB 了，heap 估计要跑很久，这次就没用。

以后怎么办

  • Codex 别一挂好几天，隔段时间 Cmd+Q 重开一下。
  • computer-use 用完的对话及时关掉。
  • 看看 ChatGPT 有没有更新。还会涨的话，就在 Codex 里提 feedback 报给 OpenAI，附上「app-server 运行 24 小时后 footprint 42 GB，几乎全是 Malloc Small」，比一句「很占内存」有用得多。

总结一下就是：

活动监视器里某个进程的内存大得离谱时，先用 footprint 看一眼分类。如果几乎全是 Malloc 的 Dirty 内存、Reclaimable 接近 0，基本就是泄漏，重启它最快。顺手记下运行时长和峰值，报 bug 的时候用得上。

BugFix｜万圣节排bug合集：点十次鼠标，蝙蝠只飞一次

发表于 2026-10-31 21:45:16 更新于 2026-10-31 21:45:16 分类于 BugFix

万圣节给博客上了个新UI，点一下鼠标，会有一群小蝙蝠从光标那儿散飞出去。

上线之后自己点了点，发现不对劲：点十次，只飞出来一次。一开始我以为是刷新率太低，先让Codex看了一轮，没看出来。后来让克（Claude）帮我查，查出来一个主bug，复现的路上又踩了好几个小坑，干脆写成一篇合集～

1. 主bug：蝙蝠在第一帧就被判死了

蝙蝠的粒子类 BatParticle，是从老烟花特效沿用下来的 Particle 继承来的。它自己重写了 update()，加了个淡入：

progress 从 0 开始，所以第一帧的 alpha 也是从 0 开始。

但它没重写 alive()，用的还是父类的：

老烟花的 alpha 是从 1 往下减的，这个判断没毛病。蝙蝠是从 0 往上涨的，第一帧要是涨得不够，直接就被判死、删掉了。

第一帧涨多少，取决于 delta，也就是这一帧离点击隔了多久：

now 是浏览器传给 requestAnimationFrame 的时间戳。浏览器有时候会把点击之后的第一帧，标成这一帧开始的时刻，这个时间可能比点击还早。一减是负数，被 Math.max(0, …) 截成 0，alpha 就是 0。

算了一下（寿命按 58 帧算）：

第一帧离点击多久 第一帧 alpha 活下来没
0ms 0 没有
0.33ms 0.0043 没有
0.67ms 0.0086 没有
0.83ms 0.0108 活了
5ms 0.0644 活了

也就是说，只要第一帧在点击后 0.8ms 以内，8 只蝙蝠一只不剩。屏幕上只剩一个 14 帧的淡橙色小圈，一闪就没，我根本没注意到它。

修法就 6 行，给蝙蝠单独写一个 alive()，只看飞行时间：

蝙蝠飞到最后 alpha 本来就会自己降到 0，所以不会出现突然消失的情况。

2. 上一轮”修”的时候，反而修得更严重了

在这之前有一次提交，叫「让蝙蝠散飞更清楚」。思路是：既然看不清，那就飞久一点、大一点。寿命从 28–34 帧调到了 52–64 帧，蝙蝠也调大了。

但第一帧的 alpha 大约是 delta / life / 0.08，寿命越长，第一帧越暗。判死的窗口从大约 0.4ms 扩到了 0.8ms。

问题根本不是”看不清”，是”根本没飞”。方向错了，越调越糟（笑）。

3. 复现坑①：自动点击，十次全成功

克用内置浏览器对旧代码真点了 10 次，10 次都有蝙蝠。

因为自动化工具发出的点击，跟真鼠标落在帧周期里的位置不一样，正好躲过了那 0.8ms。这也说明，这种bug很难靠”跑一下、点一下”测出来。

4. 复现坑②：计数器把死蝙蝠也算成了成功

测试页的思路是：拦截画布的 ctx.scale()，只有画蝙蝠时才会调它，点击后有调用，就算这次飞出来了。

结果漏了一点，动画循环是先画、后判死：

第一帧就被判死的蝙蝠，也会先用 alpha 0 画一次，被计数器算成了”成功”。后来改成统计每次点击一共画了多少次：正常飞一趟是上千次，第一帧就死的只有 32 次左右。

5. 复现坑③：有的点击一帧都没跑

改完计数器，有几次点击连光圈都没画。查了一下，是浏览器面板处于隐藏状态，requestAnimationFrame 被降到了大约一秒一帧，400ms 的统计窗口里一帧都没跑。

这是测试环境的问题，跟代码无关。

6. 复现坑④：一截图，画布就空了

想看看蝙蝠长啥样，截了个图，结果读出来的像素全是 0。

原因是截图让页面的可见性切换了一下，触发了脚本里的这句：

画布被清空了。这个其实是正常行为：页面切到后台，本来就该把特效清掉。

7. 最后的办法：自己接管帧时间戳

既然真实的帧时间不可控，那就不用它。测试页里把 requestAnimationFrame 换成手动的，每一帧带什么时间戳，由测试说了算：

然后模拟点击，第一帧喂不同的时间戳，同样的条件跑旧版和新版：

第一帧时间戳（相对点击） 旧版 新版
-8ms / -2ms / 0 / +0.3ms 蝙蝠只画了 1 帧（看不见），只剩光圈 每次飞约 62 帧
+0.8ms / +5ms / +16.7ms 正常飞约 60 帧 正常飞约 62 帧

再读一次画布像素：新版第一帧只有光圈（约 536 个点亮的像素），之后每帧 2500–3800 个，蝙蝠确实飞出去了。

模拟测试全过了，真鼠标的效果等部署之后我再点点看。

为啥上一轮没看出来

  • bug 藏在继承里：只看子类没错，只看父类也没错，放一起才错。
  • 最显眼的嫌疑点在点击处理那儿：忽略链接、选字时不触发、移动超过 7px、70ms 节流……”点十次出一次”，第一反应就是点击被过滤了。但它们全都没问题。
  • 自动化测试复现不出来（见坑①）。
  • 光圈还在，看着像”效果太弱”，于是去调大、调长（见第 2 条）。

总结一下就是：

遇到”偶尔才出现”的动画问题，别急着多点几次碰运气，先找出到底是哪个变量在随机，再把它固定下来测。这次随机的是第一帧的时间戳，接管 requestAnimationFrame 之后，问题一下就稳定复现了。
