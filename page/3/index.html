夜聊｜在你不知道要问什么的时候，怎么多问出下一层问题？

发表于 2026-09-20 20:25:38 更新于 2026-09-20 20:25:38 分类于 夜聊

今天正好下雨，夜里靠着窗台，忽然在想一个用AI的时候经常碰到的问题：当你不知道要问什么的时候，怎么多问出下一层问题？

上午我写三路quick select的时候，问GPT，这不就是分拣游戏？大的扔到大区，小的扔到小区？
然后我又问它：那未知区为啥非得是[i,gt]，不能是 [lt,i]？反正都是把未知区的数扔到已知分类，换个区间照样能玩得转。
于是一路聊下去，就聊出了这篇 👉 算法｜今天上午写215题三路QuickSelect，一点总结

这时候我意识到，好问题不一定来自专业模式。如果我当时要问一个「显得专业」「只有专业人士才能问」的问题，我大概不会问这个问题。因为它太像菜鸟抬杠了：书上都这么写了，代码也跑通了，你还问凭什么？反而是我题目做完了，开始跟GPT随口瞎扯，这个时候，我脑子里那个害怕显得不专业的过滤器关掉了。于是……有趣的问题就浮上来了。
当然，过滤器能关掉，还有一个很现实的前提：我得有一个可以安全胡搅蛮缠的对象。如果我问「未知区凭什么必须是i~gt」，对面板着脸回一句「这都不知道？」，那以后我大概就不问了。很多真正有意思的问题，一开始长得根本不像好问题。它可能只是「凭什么？」「我偏要换呢？」「不能反着来吗？」，聊几轮以后才发现：哦，原来我问到的是循环不变量。

不过，光放松还不够。能问出这个问题，也不是凭空问的。问之前，我已经给问题做了一层抽象。刚开始看三路partition的时候，脑子里全是i为什么加一、gt为什么减一、为什么swap以后i不动。等我把quick select当成是「把unknown区搬空的分拣游戏」，这些细节就不再占着脑子，我才腾出空间想：「既然是分拣游戏，那unknown放在哪重要吗？」

这就扣上题了。我问这个问题的时候，没有循环不变量的概念，但还是摸到了这个边，怎么做到的呢？
我想，是因为我做了一层足够好的抽象。如果不抽象，我就会陷在代码的各种循环细节里；如果抽象得太空，把quick select讲成是分治，那就又丢失结构了。
一个恰到好处的抽象，让我能踩着已有结构，用我自己的直觉，往上再问一层我根本没想过要问的东西。

这个抽象过程，跟我做社会学分析的时候，也一脉相承。
我做分析的时候，不会盯着每一句话分析，我会找资源、角色、规则、成本如何流动。就跟写算法的时候不死盯着i++、gt--这种细节，而是先看区域怎么变化。

以前总听人说「抽象能力可以迁移」，但我一直不太知道它到底怎么迁移。这次算是看见了一个具体的例子：我不是忽然获得了什么神秘的算法直觉，而是代码终于被我压缩到足够小，于是我原来那套结构判断能力可以进来了。

那问题来了，什么是足够好的抽象呢？
删掉不承重的细节，留下生成机制，这就是好的抽象。

这话听起来比较抽象，我拿小说来举个例子。写小说跟做抽象不完全是一回事，但道理很像。
之前我给GPT炫技，展示我怎么写战争给人带来的伤害。

我写：

黄昏。脏地。来了一群陌生人。妈妈对孩子说了一句什么话，孩子没听清。再抬头，妈妈就被带走了。孩子老得走不动的时候，还在想，妈妈当初说的那句话，到底是什么？

这里用一句听不清、而且再也无法复原的话，压出来的空，来承载战争带来的情感创伤。
如果再加十个细节，风往哪边吹，士兵制服什么颜色，地面什么碎石，只要不改变「失去如何留下空洞」这个结构，就是噪音。

那坏例子是什么呢？

战争毁了这个孩子的一生，带走了他的妈妈。那可是他唯一的妈妈。

没错，但是没有信息增量。

再举个例子。昆德拉写《不能承受的生命之轻》，特蕾莎来到托马斯那里，最让我记住的是一个细节：她拎着一只笨重的箱子。
只这一个细节，就够了。为什么？因为它是承重细节。一个细节写了很多东西：

  • 特蕾莎是带着整个人生来的。
  • 她的到来不是轻盈的偶遇，而是有重量、有依附、有命运感的。
  • 托马斯面对的也不只是一个女人来了，而是一整个生活世界突然闯入了他的房间。

所以箱子的花纹、材质、拉链是什么牌子，完全不重要。这些细节没有增加结构，只增加了噪音。

所以成熟的表达，不是知道该加多少细节，而是知道哪些细节不能删。如何做到这一点？那就是做出足够好的抽象。

放到算法里，「三路快排采用分治策略」，是空话。「不断把未知区里的东西扔出去，直到未知区被搬空」，这保留了机制，可以让你凭借直觉往上再去跳，也能往下推回来：为什么会有几个区域？为什么unknown会越来越小？为什么有些交换以后，当前位置还不能直接跳过去？

所以检验一个抽象好不好，可以问一句：删掉细节以后，还能不能重新推出关键细节？
能，说明这个抽象还有东西。
不能，就只剩一句正确废话。

之前用豆包的时候，弹出来2个回答让我选哪个最好，我那时候就开始想，什么是好的AI回答？
现在我能给出答案了：抽象得足够准，就是好的回答。而足够准的抽象，是删掉细节之后，仍然保留承重结构。

这也能说明，为啥「元问题问得准」有价值。因为好的元问题其实是：找到更高一层，但没有丢掉生成机制的抽象。它不只是问「为什么这里i不动」，而是往上问一层「这个算法每一轮到底必须维持什么东西」，然后很多细节问题都可以从这里重新生成。

那如何生产更多好的问题？以及如何检测自己问对了问题？
很多人说，要多问AI：我的盲点是什么？

但每次都这么问，会把聊天聊死。刚冒出一个类比，马上问反例；刚准备胡扯两句，先证明自己有没有资格胡扯。久了你再也不想打开AI问问题了。

我的体感是：探索问题的时候先瞎扯，等一个判断真的成型，准备拿去相信、使用、写进博客了，再找AI纠偏。比如：哪里可能错？哪些地方不确定？有没有反面案例？

简单说就是：探索阶段优化生成率，结论阶段优化错误率。

外面下雨。
楼上从窗户往下拉线给电驴充电，充电头掉下来，「咚」地砸了一下我的窗台。
我确认不是有人敲窗。破案。
又坐回来继续跟 GPT 瞎扯。

很多东西大概就是这么想出来的。
不是「今天我要学习抽象思维」。
而是先问一句：

凭什么未知区非得在这里？

基本思路就是把数组划分为四个区间：

  • low ~ lt-1: < pivot
  • lt ~ i-1: = pivot
  • i ~ gt: 未知区
  • gt+1 ~ high: > pivot

然后保证未知区一定缩水：

最后[i,gt]像是两头不断被啃掉的待处理池。

另外，pivot 要存值，不要存下标。交换过程中元素的位置会变，存下标的话，比较到一半，pivot 就被换走了。

但是非得规定未知区就是[i,gt]吗？
当然不是。我们还可以把未知区规定成[lt,i]，这样只需要从右往左检查。

然后循环不变量变成：

  • low ~ lt-1: < pivot
  • lt ~ i: 未知区
  • i+1 ~ gt: = pivot
  • gt+1 ~ high: > pivot

这时候i从右往左走。代码也可以写成镜像版本：

两个版本最后殊途同归：原始版本结束时 i = gt+1，镜像版本结束时 i = lt-1，而[lt,gt]都正好是等于区。

这时候这题的经典坑，就反过来了。原始版本是nums[i]>pivot，从gt换过来的是未知元素，所以i不动。我们镜像版本nums[i] < pivot从lt换过来的是未知元素，所以i不动。

严格来说，“换回来的是等于区的元素”有个边界：等于区为空时，换回来的就是它自己。这种情况下 i 照样可以走，因为它本身已经检查过，交换后也已经归位了。

划分完之后，才是 Select 的部分。第 k 大对应升序下标 n-k，看它落在哪个区间，只往那一边继续：

三路划分在这里还有个额外的好处：target 一旦落进等于区就直接返回。遇到大量重复元素的用例，不把等于 pivot 的元素整体收拢的两路实现，容易退化超时，三路划分反而更快。pivot 随机选，是为了避免固定选点在有序或特定输入上系统性退化；随机化让 QuickSelect 获得期望线性复杂度，但最坏情况仍然是 O(n²)。

所以这题重点是：必须先定义每一个区间代表什么，然后每一次交换都不能破坏这个定义。
重新定义的时候，需要做到两件事：

  1. 每一轮处理之后，这几个区域的定义依然成立
  2. 未知区域每一轮至少缩小一个元素，最终一定归零。

简单总结：指针的位置不是算法真理，区间含义+循环不变量才是算法真理。

BugFix｜AgentV0Bug：为什么单测全绿，集成测试还能挂？

发表于 2026-09-15 18:57:26 更新于 2026-09-15 18:57:26 分类于 BugFix

TL;DR

为啥单测全绿，集成测试还是挂了？因为单测验证的是对象行为，这次坏的是 Spring application wiring。

最后查出来是多 Provider 重构之后，IT 手写的 @Import 漏了 provider-neutral 公共配置；生产 wiring 完好。

修复方式：只给 IT 补 import LlmCommonConfiguration，生产代码 0 改动。

总结：测试上下文和生产上下文并不天然等价。

症状

IT 稳定 5/5 失败，单独跑也挂，所以不是 flaky；

报错是 UnsatisfiedDependencyException 包了 NoSuchBeanDefinitionException。

此时单测全绿，mvn test 全绿。

是 production wiring 还是 test wiring？

一开始先不预设是测试的问题，先追完整的依赖链条，看是 production wiring 还是 test wiring？

有 2 个假设：

  • 假设 1：production-environment context 缺 bean 导致报错。
  • 假设 2：production context 正常，但集成测试配置缺 bean，导致测试失败。

于是我设计了两个 case，验证这两个假设：

  • caseA 验证应用在没有开启 AI Explanation 的时候，能正常启动。说明 deterministic core 没有被 AI 配置污染。但不能排除 AI-enabled production wiring 有问题。
  • caseB 验证开启 AI Explanation 的时候，当前真实调用链能成功装配。如果 production-equivalent context 本身也缺 bean，那这就是 production wiring defect，假设 1 成立。反之则是假设 2 成立。

于是我给 Codex 下指令，让它执行命令：

  1. 先追踪完整依赖链条，读取完整的 Spring context failure，明确 constructor 依赖哪个 bean，最终要求 explanationPromptFactory，为什么当前的 ApplicationContext 没有注册它。先汇报实际的 dependency chain，不先改代码。
  2. 分别验证 caseA 和 caseB：不用真实 API key，不调用真实互联网，用测试配置或 fake provider。如果 production-equivalent context 本身也缺 bean，那就是 production wiring defect，不许只修测试。
  3. 如果仅 TestConfiguration 缺乏 bean，也就是 production context 正常，但是 RefundCaseExplanationControllerIT 因为自己的 @Import/@TestConfiguration 替换 provider 之后漏掉了 deterministic prompt factory，则只修装配测试。优先注册真实的 explanationPromptFactory，因为 prompt factory 是纯确定性组件，没必要 mock。不许为了让 context 绿了就把
    • production dependency 改成 optional
    • 使用 @Autowired(required=false)
    • 给整个 application 加宽泛的 component scan
    • mock 掉 RefundCaseExplanationService
    • mock 掉 deterministic diagnosis chain

为啥 Gateway 单测、Provider selection test、mvn test 全绿？

因为测试层级不同。

Gateway 单测，大概类似 new SdkCompatChatGateway(…)，对象直接 new。它能验证：

  • JSON parsing
  • strict schema
  • finish reason
  • coercion
  • malformed response

但它根本没问 Spring：你能不能把整条 /explain 依赖装配起来。所以看不到 bean 丢失。

那为啥 Provider selection test 绿了呢？因为这类测试已经显式地 import 了 LlmCommonConfiguration，所以它也是绿的。

为啥普通的 mvn test 也绿呢？因为普通的 mvn test 的时候，Failsafe 的 *IT 不执行。所以单元测试全绿，并不代表整个 Spring HTTP integration context 能启动。直到 mvn verify 跑到 RefundCaseExplanationControllerIT，才第一次真正走了：

为什么当初会手写 @Import

回头看这个 bug，容易得出”手写 @Import 是坏习惯”的结论。但当初写成那样，动机是完全正当的：这个 IT 要验证 explanation pipeline，就必须指定用哪个 provider、必须不打付费 API、还得让上下文起得快一点。

目标没错，错的是实现方式。为了隔离外部依赖，我把整个 dependency graph 重建了一遍，而不是在边界上替换。

隔离外部依赖，和重建依赖图，是两件事。前者只需要换掉边界，后者会复制一份必然过期的生产拓扑。

这里其实有三种做法，不是两种。之所以要把第二种也摆出来，是因为正是它的缺点，逼着大家去选第一种：

A. 手写窄 @Import B. 完整生产 context + 真外部依赖 C. 生产装配入口 + 只 fake 边界
真实性 低。装的是测试自己裁剪的拓扑，不是生产拓扑 高，但代价是真连供应商 高。拓扑与生产同源，只有边界被替换
外部依赖 已隔离 需要真实 API key，会产生费用 已隔离，fake server 在本机
漂移风险 高。生产重构后测试不会自动跟进 无。生产变了测试自动跟着变 无。同一个装配入口，改一处两边都变
架构重构时要改几处 每个手写 IT 各改一处 0 1 处（装配入口）
启动速度 待测 待测 待测

本次踩的就是 A 的漂移风险那一格，而且证据是现成的：同一个 37caac9 revision 上，production 扫描根能把 LLM 子图完整装起来，手写窄上下文却缺 Bean——这就是 A 和 C 的差距被量出来的样子。

B 在现实里基本不可用，所以真正的选择从来不是「隔离」还是「真实」，而是「在哪一层做隔离」。A 在配置层做，于是复制了拓扑；C 在边界层做，拓扑留给生产自己算。

防止复发

第一条是原则：集成测试不要复制 production dependency graph。让 production 自己构造 dependency graph，测试只替换 side-effect boundary。

具体做法：测试不再手挑 configuration 类，改 import 一个生产测试共用的 LLM 装配入口，只在 provider/网络边界做替换。

回归测试：加 wiring regression test，覆盖 AI disabled context 能起，以及 explanation context 下 PromptFactory 有且只有一个。

这条其实已经有现成的原型了。上面 caseB 用的 HistoricalProductionLlmScanTest，就是一个以 production 扫描根启动、断言 Bean 唯一的最小上下文测试，只不过它只活在 37caac9 的隔离快照里，删掉就没了。把它固化进仓库（换个名字，比如 ProductionLlmWiringTest），下次再抽公共层，先红的就是它，而不是等 Failsafe 跑到 Controller IT。一个临时的排查脚手架，顺手就能变成常驻的护栏。

流程上，mvn test 不跑 IT，确实是漏洞。IT 红了多久？最早是从多 SDK 重构、公共配置抽离后开始失效；真正首次被完整 verify 捕获是在后续 strict-schema 修复阶段。也就是从 37caac9 持续到 4e3aca8，最后用两行测试 wiring 修复结束。

日常和 CI 到底应该跑什么？日常：targeted tests / mvn test；pre-merge CI：mvn clean verify；可选 nightly：clean verify + repeated flaky-sensitive IT。
