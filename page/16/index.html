技术手记｜风控踩坑，链路断层

发表于 2026-02-13 14:29:32 更新于 2026-02-13 14:29:32 分类于 技术手记

最近登录模块风控链路写完测试，发现新毛病，频控只在code错误时才计数）。
画个图就是：用户请求发送短信->发送成功->频控不计数，只有：验证码错误 -> 频控+1

这个问题出现，是把风控逻辑混在业务逻辑一起写了。具体写法是：

  1. 发短信的时候，不检查手机号是否被风控
  2. 登录的时候，检查手机号是否被风控

后续改正：做两套风控系统。

  1. 发短信接口频控（目的：防刷/防低成本攻击）
    • 必须在发短信之前执行（成功失败都计数）：
      1. 校验IP频率
      2. 校验设备ID频率
      3. 校验手机号频率
      4. 通过之后调用短信网关
  2. 验证码校验错误次数（登录级）
    • 验证码错误 -> 手机号错误次数+1
    • 超过5次->锁手机号登录

当手机号被锁的时候，需要同时影响：

  • 发短信
  • 验证码登录
  • 刷新token（如果有）

也就是说：

改之后的发短信接口流程是：

  1. 请求进来
  2. 检查IP是否被锁
  3. 检查设备ID是否被锁
  4. 检查手机号是否被锁
  5. 检查手机号发送频率
  6. 检查IP发生频率
  7. 全部通过，发送短信
  8. 发送成功之后记录频次

验证码登录流程设计：

  1. 请求进来
  2. 检查手机号是否被锁
  3. 校验验证码
    • 正确：清除错误次数
    • 错误：错误次数+1，超过5次，锁手机号30分钟

另写法上需要改进的是，把风控逻辑从业务逻辑里抽出来，做个拦截器。具体写法是：

  1. 登录前（IP/设备ID)，用于：登录接口，发送验证码，注册等无需token的接口
  2. 登录后（UserId/AccountId/Token来源等），所有需要登录态的业务接口，比如：发帖，评论，下单。

日常记录｜用codex app审核代码，爽～，顺带整理了一份codex审核代码的prompt

发表于 2026-02-10 20:40:04 更新于 2026-02-10 20:40:04 分类于 日常生活 ， 技术手记

最近，用codex审核代码，很爽。
今天下午测了一下午的bug，token存错了，结果codex花了2分钟帮我审核出来，然后打了补丁。

另，codex审核代码要写清楚的几件事：

  1. 角色：你是一个资深后端 reviewer
  2. 文件名&方法名
  3. 要审核的方法的功能+实现的目标（可以从接口文档 or 设计文档里copy）
  4. 输出内容：
    • 按照优先级输出bug，说明不改会发生什么事故
    • 打Patch（最小补丁，diff风格）
    • 给可复现的回归用例
    • 额外需要指出的问题
  5. 工程约束
    • 项目技术栈
    • 必须指出的项目特别用法：
      • 比如这个项目里，redis缓存，用的StringRedisTemplate
    • 返回结构
    • 改动风格
      • 比如：尽量最小改动，不要重写整个类
    • 减少幻觉（当模型不确定的时候，让它假设，而不是直接让它猜之后改）：
      • 比如：如果你无法从代码中判断某个常量，错误码，字段含义，请标注假设点，不要自行编造。

最后：夸一下codex app，比之前的terminal端方便多了。

进步点：

  1. UI更清晰，可以轻松回溯某个项目的会话
  2. 改动之后，可以直接定位到项目文件
  3. 可以编辑skills（虽然我还不会用）
  4. 默认跑沙盒里，不会动项目文件，除非你给权限。

最近马上春节，千问（阿里）做活动，下载app送25元无门槛优惠券。

要求：

  1. 下载千问app
  2. 注册
  3. 授权淘宝闪购
  4. 授权支付宝
  5. 必须在千问app内完成点单，在淘宝闪购内部看不到千问发的优惠券

这次活动的特点是：真金白银砸钱，门槛极低，微博上热搜，扩圈度高。

那为啥阿里要花钱砸千问呢？

  1. 千问抢的是「AI+生活消费」第一入口位
  2. 千问卖的不是模型，是使用路径

腾讯不需要你想起元宝，只需要你在原有行为里顺带用一下。

所以元宝是防御性部署，千问是进攻型营销。

技术手记｜代码审核新思路

发表于 2026-02-09 11:42:30 更新于 2026-02-09 11:42:30 分类于 技术手记

SOP

写代码->本地跑最小门槛

  • formatter/lint/静态检查（能自动化就自动化）
  • 单测（至少新增/改动路径覆盖到）

Codex code-level review -> 产出报告到docs/codex-reviews

  • Codex只盯：可读性，明显bug，边界条件，并发/资源泄露，日志与异常处理，潜在的NPE，SQL/缓存误用，未处理的失败路径
  • 报告要可检索：按照日期+模块命名，例如：2026-02-08-login-token.md

我按照报告改 -> 再跑测试

  • 这一步配合一个「勾选清单」，避免改着改着把主线改丢

Thinking 做第二层 review（设计/上限风险/功能缺口）

  • 重点盯：接口契约，幂等性，降级，限流，可观测性，缓存一致性，事务边界，并发与重试策略，数据增长后的性能拐点，最容易上线炸的路径。

压测与文档收尾

  • 压测不是跑一下，而是：场景，数据规模，并发模型，指标口径，瓶颈定位，结论与改动建议
  • 文档：模块介绍/接口文档/关键设计决策（为什么这么做，不那么做）

这个设计的优点

  • 降低心里摩擦：不需要每次凭意志力信自己对还是错，而是把信任外包给流程，流程跑完，人就安心。
  • 可复盘，可证明：docs/codex-reviews + 压测文档，做成工程能力证据链
  • 把注意力分层：Codex抓底层bug（拼写，分支遗漏，NPE，资源关闭，日志），Thinking抓系统性炸点（幂等，重试风暴，缓存击穿，慢SQL，错误码契约）
  • 形成可重复的“模块闭环”：不是一直写，而是交付一个个完成的态的模块

主要风险点

  1. 文档负债风险
    • 如果每次review都提交一次review报告，很快会被文档淹死
    • 解决：只有以下情况固化到repo
      • 新模块完成
      • 关键重构
      • 性能优化前后
      • 上线前检查
    • 其他最小改动只留在PR描述或者临时notes
  2. 报告噪音与形式主义
    • Codex容易给一堆看起来很对但不关键的建议
    • 解决：让报告强制分级
      • P0:必须改，会上线炸
      • P1:应该改，影响可维护/性能
      • P2:可选优化
  3. 泄漏风险
    • 把review 文档提交到repo，容易不小心带上：内部url，token，真实数据样例，库表敏感字段。
    • 解决：报告模板里加一条规则：不得出现真实密钥/真实用户数据/完整链接串，样例一律脱敏
  4. 双review导致节奏变慢
    • 每个模块看起来更慢，但这算是返工减少的慢
    • 解决：
      • 对小改动走“轻量链路”：本地检查 -> 小范围Codex review（不落文档）-> 测试；
      • 只有交付级模块才走全链路

输出格式

docs/codex-reviews/报告模板

  • 变更摘要
  • Codex发现
    • P0：问题/影响/建议修改点（指到文件+函数）
    • P1: …
    • P2: …
  • 已经处理的清单（checkbox)
  • 遗留项（明确说明为什么不改+风险说明）

压测文档最小模板

  • 环境（机器，JVM参数，DB/Redis规格，版本）
  • 场景（接口，数据量，并发，持续时间，思考时间）
  • 指标（P50/P95/P99，吞吐，错误率，CPU/GC/DB慢查询）
  • 结论（瓶颈点&下一步优化路线）

自动化链路

  • PR自动跑：lint + test + 静态扫描（SpotBugs/Checkstyle/Semgrep之类）

前情回顾：
我的一个方法流程是：

  1. redis读写（业务状态）
  2. DB读写
  3. redis读写（缓存态）

我纠结的问题点：

  1. 目前情况会导致事务回滚DB数据，而redis数据没有同步回滚
  2. 考虑afterCommit，提交事务之后再读写redis，但因为流程不可拆，所以该方案不行。

我考虑的解决方案：

  1. 显示补偿，不是强一致。
  2. Canal

方案1如何操作：

该方案适合：

  1. 状态机
  2. 次数扣减
  3. workflow

方案2Canal

  1. 第一步redis，自己写
  2. 第三步redis，交给Canal

Canal能做的：

  1. 监听DB binlog
  2. DB commit之后，异步更新redis/es/mq

Canal解决的问题是：「DB -> Redis的单向同步」

Canal使用场景：

  1. 多表多服务共享redis
  2. 读多写少
  3. 强烈不想在业务代码里碰缓存
  4. 接受秒级延迟
  5. 有运维精力

另，redis的状态如何区分？

  • 业务态Redis（不需要强一致，出问题靠TTL/补偿，不需要进事务）
    • 限流
    • 去重
    • 幂等
    • 状态机 step
    • 分布式锁
  • 缓存态Redis（DB派生）（严格afterCommit，删除缓存/重建）
    • 详情缓存
    • 聚合结果
