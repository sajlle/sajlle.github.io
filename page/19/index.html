技术手记｜AI会抢哪些人的饭碗？哪些技能在AI时代越来越稀缺？

发表于 2026-03-01 13:44:56 更新于 2026-03-01 13:44:56 分类于 技术手记

这也是2月26日看论文的总结。当天我是5点睡觉，然后中午起来，傍晚18点吃完饭之后，我到三叔家看论文。
这篇也是arXiv上的论文，名字叫：Some Simple Economics of AGI。

论文观点我总结一下：

  1. AGI时代真正的瓶颈不是智能/执行，而是人类验证带宽。
  2. 经济分区从「例行/非例行」切换为「可测量/不可测量」，自动化会很便宜，但验证不可行的盲区会扩张。
  3. 过度部署会产生系统性外部性，未验证部署份额与失配叠加形成特洛伊木马外部性，表面指标/产出上涨，真实效用与控制力被掏空。
  4. 人类在环并不稳态：一方面初级岗位被吞掉，另一方面专家把经验写进数据加速自我淘汰，结果验证层既更重要，又更稀缺。
  5. 价值/护城河迁移：从产出能力迁移到可验证的真相，可追溯性，以及能承保的责任，并出现Liability-as-a-Service

其中几个点展开说：

  1. 生成接近0成本，越来越多人可以做出类似专业的作品，但这些作品到底行不行，需要验证。也就是说，生成不重要，验证生成才重要
  2. 越强的系统越会优化你给它的测量指标，导致指标越强，Goodhart 越快；验证越慢，漂移越隐蔽。
  3. Missing Junior Loop会是个很现实的问题。初级工作自动化，未来的专家从哪里来呢？专家少，组织会越来越依赖能背锅的老手，而老手又更快被消耗完。

对个人来说，需要做的转变是：

  1. 把自己定位成「意图导演 + 验证者」，而不是执行工具人，当智能变得廉价之后，人类的工作更可能迁移到意图，验证，承保。
  2. 用AI做合成练习，加速熟练度。但要注意验收，否则就是把自己训练成会产出但不会验收的人。

对组织的影响：

  1. 把验证当「生产技术」，不是合规成本：比如，可观测性、审计日志、回放、压测、灰度、事故复盘机制。
  2. 组织结构会自然走向「夹心」：需求/意图层更强、执行层自动化、验证与背锅层更稀缺——这会决定岗位价值与晋升路径。

技术手记｜最近看论文有感：用AI，而不是把脑子外包给AI

发表于 2026-03-01 13:22:08 更新于 2026-03-01 13:22:08 分类于 技术手记

最近看arXiv上的文章，对比了用AI和不用AI的人，学习技能效果如何。自媒体把这个文章结论放大成，用AI会让你技能下降。
但实际更值得看的是：文章把AI组的使用方式分成6种persona，有的模式几乎不伤学习，有的模式直接把学习效果击穿。

论文里的高分模式有：

  1. Generation-Then-Comprehension：先生成，再追问理解 → 86%
  2. Hybrid Code-Explanation：要代码同时要解释 → 68%
  3. Conceptual Inquiry：只问概念，错误自己解决 → 65%

低分模式有：

  1. Iterative AI Debugging：反复让AI排障/验证（5–15问）→ 24%（最低）
  2. AI Delegation：只让AI写代码直接贴 → 39%
  3. Progressive AI Reliance：先问两句，后面逐步全交给AI → 35%

另，作者提到一点：debugging类提问占比越高，完成越慢、测验分越低。

看完论文，我总结了一下我用AI的方式如何避免陷入低分模式。

我这边的用AI学习的模式是：

  1. 问概念/框架/边界条件 -> 拿到信息地图（AI的作用是信息降噪）
  2. 我写最垃圾的demo -> 在摩擦里建模（自己捣鼓）
  3. AI review + 追问A/B取舍 -> 把建模压缩成可迁移规则（AI验证我盲点&给最佳实践模板）
  4. 我再改一轮 -> 完成「建模 -> 压缩 」的闭环（我照着最佳实践自己捣鼓）

如何判断啥时候，该自己捣鼓呢？

  1. 我说不清：这个模块的输入输出/失败模式
  2. 我不知道：这里为什么用A不用B
  3. 我能抄出来，但换个约束就不会改
    这时候AI最适合做：给关键词，给对比维度，给边界清单，给测试用例思路，而不是给最终实现

如何判断啥时候，可以照着最佳实践套模板

  1. 自己能写一个跑得通的「丑实现」
  2. 自己能解释关键取舍「哪怕不优雅」
  3. 能改约束并且重构「比如从单机限流 -> 分布式限流」
    这时候AI最适合做：review，重构建议，性能/安全/可观测性补强，替代方案对比

另，多瞎扯一句：其实非AI辅助的学习也类似，如果没有自己踩坑建模，直接被喂最优解，学习效果反而不如自己瞎捣鼓踩坑之后再看最优解效果好。

日常记录｜我是同辈分孩子里，跳轨最激烈的一个，这是偶然吗？我从博弈的角度拆解一下

发表于 2026-03-01 12:05:45 更新于 2026-03-01 12:05:45 分类于 日常记录 ， 家庭尸检

如题。这很有趣，我选择彻底跳轨，不是变轨，不是在家长面前表演听话，是个性使然，还是策略选择？
正好我有个同岁的堂姐，跟我家一样卖早餐。她是变轨，我是跳轨。我来对比一下，就清晰很多了。

堂姐和我童年对比

我做个简单对比：

  • 堂姐中学成绩一般，三叔送她学画画，考艺术生。我如果成绩一般，就直接辍学打工去了
  • 堂姐家跟我家一样卖早餐的，她父母没有强迫她7～19岁寒暑假周六日当童工。我家我干到19岁，不是因为19岁我父母良心发现，而是19岁，我到外地上大学去了
  • 堂姐小时候有玩具（我去她家里玩，一起玩这些），我是7岁找家里帮工（对7岁我家有帮工，但我还是要被叫起来干活儿）借了5毛钱买洋娃娃，我妈知道打了我一顿。10岁（我帮忙三年了），买了一个洋娃娃（3块，被我妈说浪费钱），用的是我干童工的钱。我干一天，2块钱。
  • 堂姐这边卧室房间大&通风&装修都好，我这边卧室靠近楼道/窗户不通风/装修最差/没有空调。

我以为家庭是利益共同体，实际我家是按照角色分配收益，按照能力分配责任

我一开始卖力干童工，以为家庭是利益共同体，但我家实际是按照角色分配收益，按照能力分配责任：

  • 利益&资源：按照角色分配，谁该被照顾，谁该忍，谁该背锅，都分配好角色了
  • 责任：按照能力分配，有能力=抗更多锅，弱的/闹的=责任更小，收益更大，资源被倾斜
  • 付出不产生谈判权：反而成了义务证据

这就出现一种悖论：我家里，越能干越吃亏，越讲道理越被甩锅。

我家是零和博弈，三叔家是非零和博弈

三叔家那边，是底线协议（非零和协议）

  • 女儿是外人也好，至少底线是不把她当耗材
  • 成绩不行 -> 允许身份置换（艺术）
  • 摩擦存在，但关系可维持：说明家里允许一定程度偏离模板

我家协议（零和）

  • 角色先分配：我被塞「能干，能忍，能顶」的位置
  • 角色按照资源走，责任按照能力走：越能干越该扛
  • 长期争吵不是偶然，是系统自洽，不反抗就被消耗，一反抗就被围剿

环境导致我跟堂姐的策略不同

所以我跟堂姐的策略就非常不同了：

  • 堂姐是变轨：跟家里有摩擦，但不断链，不退出，至少在人情场上，还演一下体面。对她来说，变轨收益高，因为她不撕破脸，也不会被拉回工具人&背锅位。
  • 我是跳轨：跟家里激烈摩擦，退出所有家务决策/不提供信息/不参与安排/不在人情场上演家庭和睦。对我来说，跳轨收益更高，因为不跳轨，只是变轨的话，依旧会被拉回工具人&背锅位。

总结：我们选择的策略不同，不单是个性使然，更像是在不同环境下，选择的最优博弈方式

简单总结：我是同辈孩子里，跳轨最激烈，跟家里摩擦最大的孩子，不是偶然，是我家的规则根本没给我留出口，跳轨是最优策略。否则我就会被拉回工具人位。

日常记录｜给我家做了一个结构画像，我家冲突激烈，不是偶然

强制度化童工化家庭的结构画像

系统定义

目标（表面）：

维持家庭生计，店面运转，家务效率，面子秩序

目标（真实）：

用“持续征用”制造可控性，稳定父母的焦虑与权威，降低对外部资源的依赖成本。

特征：

把孩子当作长期劳动力与情绪缓冲器，形成稳定排班机制（7–19岁、寒暑假、周末、全年执行）

输入

资源约束

  • 现金流紧张/不稳定（或者对不稳定高度恐惧）
  • 人手不足（或者不愿雇人/不信任外人/不想付出雇佣成本）

认知与价值观输入

  • 闲着 = 败家/变坏/不听话
  • 吃苦 = 正当性
  • 孩子是家庭资产/劳动力储备

情绪输入

  • 父母长期焦虑（钱/面子/亲戚比较/控制感不足）
  • 对不确定性低耐受 -> 需要立刻做点什么来「看见掌控」

环境触发器

  • 亲戚来访/面子局/装修/婚丧喜事/赶集旺季
  • 任何「外部变动」都会提升系统压力，从而增强对孩子的征用频率

核心规则

角色先分配

  • 我：可用/能干/该忍/该顶
  • 我的价值不是「发展」，而是「可调度性」

这导致：贡献越多，责任越多，但权限不增加。【很典型的反激励】

时间不属于我（属于父母）

  • 我的时间默认归家庭所有
  • 个人时间需要「批准/赏赐」，且可以被随时撤销

「劳动 = 服从」的绑定

  • 干活儿不仅是产出，更是服从验证
  • 让我帮忙是为了确认权威，我是否依旧可调度

无补偿机制

  • 别人家是「打一巴掌给一颗糖」
  • 我家是「打一巴掌再骂一顿」
    => 系统不给出口，不提供可恢复的情绪回路

甩锅协议

  • 建议者会被当作责任源头（我说一句 = 我该负责推进）
  • 承担者回被当作默认义务（我做一次 = 我该一直做）
    => 系统鼓励：「不承担的人永远更安全」

断章取义接口

  • 说话被截取成「可用于外部甩锅/内部指责」的片段
  • 语言不是用来协作，而是用来博弈与责任转移
    => 语言成为高风险输入源头

执行流

  1. 外部压力/内部焦虑上升
  2. 父母启动「控制回路」：寻找可被立刻调度的对象
  3. 选择最稳定可控资源 => 我
  4. 以道德语言封装指令
    • 你闲着干嘛
    • 一家人还计较
    • 你不干谁干
  5. 被拉进执行 -> 系统短期稳定（父母获得掌控感）
  6. 我试图协商/表达 -> 被判为「管太多/顶嘴」
  7. 系统通过争吵/羞辱/冷暴力把我压回可用状态
  8. 周期循环，直到我出现跳轨行为

输出（系统产物）

对父母

  • 即时掌控感（焦虑被转移）
  • 获得廉价劳动力与情绪泄压对象
  • 维持我在管家/我在当父母的叙事

对我

  • 极强的逆境执行力与工具理性
  • 对「被召唤/被打断」高度敏感
  • 需要确认安全边界才能投入个人事务
  • 对「解释/沟通」形成条件性恐惧（说话 = 被利用）

副作用

行为层

  • 形成「先做出成果才配休息」的逻辑
  • 容易进入「爆肝 -> 崩溃 -> 自责」循环
  • 对家庭事务产生全面回避（因为参与 = 被吸血）

情绪层

  • 休息羞耻感/闲置焦虑
  • 对亲密关系的「被征用恐惧」
  • 轻微的「反补偿冲动」：只要能自主，就想自主

关系层

  • 家庭沟通变零和博弈
    • 我赢了=他们输了
    • 我解释=我给接口
    • 我沉默=自保
  • 最终导向：退出式和平

系统的故障模式

自证预言（希腊神话模式）

父母为了防止独立而控制我
-> 控制过载
-> 我只能更激烈的跳轨独立
-> 父母说：「看吧，她就是要跑」
-> 控制更强（进一步加速分离）

反激励导致「能力惩罚」

我越是能干越被用，越被骂
-> 我的策略变成：不显能，不建议，不承担
-> 家庭效率更低，冲突更高
-> 父母更焦虑 -> 更想征用我（恶性循环）

技术手记｜写写Spring MVC的流程，Filter拦截了啥？Interceptor拦截了啥？

发表于 2026-02-23 15:07:41 更新于 2026-02-23 15:07:41 分类于 技术手记

来，先上一个一次HTTP请求在Spring Boot里走过的路径（单请求路径的横切面）

Filter：拦截的是进入和离开DispatcherServlet之前的所有请求，面向servlet层。

  • Client -> Filter -> DispatcherServlet -> Filter -> Client

Interceptor： 拦截的是进入Controller前后的所有请求，面向Spring MVC层

  • DispatcherServlet -> handlerMapping -> Interceptor.preHandle -> controller -> Interceptor.postHandle -> View/ MessageConverter -> Interceptor.afterCompletion -> DispatcherServlet

视觉化的总结：

  • Filter包住了dispatcherServlet
  • Interceptor包住了controller -> view/ messageConverter，controller执行之前塞preHandle，controller执行之后塞postHandle，视图渲染之前，塞afterCompletion

Spring MVC里的DispatcherServlet到底干啥了？

  1. 找到执行哪个handler
    • HandlerMapping 根据URL，HTTP Method，参数等，找到匹配的Handler
      • 通常是@RequestMapping/@GetMapping里的某个Controller方法
  2. 决定怎么执行这个handler
    • HandlerAdapter 把找到的handler用正确的方式调用起来
      • 对 @Controller的方法，走RequestMappingHandlerAdapter
  3. 参数绑定 + 调用Controller
    • 把JSON body/ query/ path解析成DTO
    • 做参数校验（比如 @Valid）
    • 调用 Controller 方法，拿到返回值
  4. 处理返回值
    • 返回JSON @RequestBody或者@RestController
      • 走HttpMessageConverter （比如Jackson），把对象写到response body
    • 返回页面（View）： ModelAndView
  5. 走异常处理
    • 抛出异常的时候，会走HandlerExceptionResolver
      • @ControllerAdvice / @ExceptionHandler

人话版本：找到方法，执行方法，解析结果，异常处理

  • 找到controller里的方法（HandlerMapping/@RequestMapping等等）
  • 调用方法（handlerAdapter/RequestMappingHandlerAdapter）
  • 解析参数（嗯，这时候接触到方法了，才解析参数）。（参数变DTO，校验参数，调用方法，拿到返回值）
  • 把返回值塞给responseBody(如果返回json),MessageConverter，或者返回view（如果是jsp前后端耦合）
  • 抛出异常（HandlerExceptionResolver, @ExceptionHandler/@ControllerAdvice)

Interceptor拦截了啥？

  1. preHandle(request, response, handler)
    • 发生在拿到handler之后，执行handler之前，拿到的是哪个controller的哪个方法
    • 可以返回false终止请求
    • 用途：需要知道这是哪个业务接口/哪个注解的策略
  2. postHandle(reques, response, handler)
    • 发生在Controller执行之后，渲染之前
    • 请求走到Controller，且没有异常
    • 可以改 ModelAndView，纯JSON场景用处少
  3. afterCompletion(request, respons, handler, ex)
    • 请求整个完成之后，包括异常/视图渲染/JSON写出之后
    • 最适合做：资源清理，耗时统计收尾，MDC清理
    • 即使异常也会被调用，这也是它比postHandle更可靠的地方

人话版本总结：

  • preHandle：适合需要知道哪个业务接口
  • postHandle：请求走到这里且无异常，有异常可能不走这里
  • afterCompletion：即使异常也被调用，适合请求执行完之后的资源清理等收尾工作

Filter到底拦截了啥？

Filter（javax.servlet.Filter/ jakarta.servlet.Filter）只有一个核心doFilter(request, response,chain) ，作用是：

  • 是否继续chain.doFilter()，让请求往后走
  • 在chain.doFilter前后做什么

Filter能力比较底层：

  • Filter能在Spring没找Controller之前拦截
  • 对所有路径都可能生效（包括静态资源，非MVC servlet等）
  • 包裹request/response(wrapper)，做I/O处理，比如缓存body，加解密，统一压缩等

技术手记｜Java后端几个模式～

发表于 2026-02-22 19:42:58 更新于 2026-02-22 19:42:58 分类于 技术手记

今天我问ChatGPT，我之前写代码没思路，可能是对模式不了解？
GPT回我：要不要我给你几个模型？
于是这篇博客就有了。（笑）

今天（2026-02-22），我只记录模式，明天或者后天，我再补上实际的案例。

并发与一致性的常见模式

Check-Then-Act（先检查再执行）

典型场景：

  • 判断库存>0之后再扣减
  • 判断是否锁定再加锁
  • 判断是否存在再插入

问题：

  • 检查和执行分离，会被并发打穿

解决：

  • 原子操作（Lua）
  • 乐观锁
  • CAS
  • 数据库唯一索引

Lost Update（更新丢失）

典型场景

  • 两个线程读取同一值
  • 修改后覆盖

解决

  • 乐观锁 version
  • 行锁
  • CAS

Double Submit（重复提交）

典型

  • 用户点两次按钮
  • 重复下单

解决

  • 幂等 token
  • 唯一索引
  • 状态机控制

Cache Breakdown（缓存击穿）

典型

  • 热点Key过期
  • 同时大量请求打DB

解决

  • 互斥锁
  • 预热
  • 永不过期 + 异步刷新

Cache Penetration（缓存穿透）

典型

  • 查询不存在数据
  • 每次打DB

解决

  • 空值缓存
  • 布隆过滤器

Thundering Herd（惊群效应）

典型

  • 高峰期瞬间请求暴涨

解决

  • 限流
  • 排队
  • 削峰填谷

架构思维模式

Fail Fast（快速失败）

与其被慢慢拖死，不如：

  • 限流
  • 降级
  • 熔断

Graceful Degradation（优雅降级）

比如：

  • 评论系统挂了不影响主流程
  • 风控策略收紧

Idempotency（幂等性）

重复请求不影响结果

State Machine（状态机）

登录，订单，风控其实都可以用状态流控制
