生活观察｜千问活动红包比元宝大，是腾讯没钱砸活动吗？（坏笑）

发表于 2026-02-09 13:14:02 更新于 2026-02-09 13:14:02 分类于 日常记录 ， 生活观察

最近马上春节，千问（阿里）做活动，下载app送25元无门槛优惠券。

要求：

  1. 下载千问app
  2. 注册
  3. 授权淘宝闪购
  4. 授权支付宝
  5. 必须在千问app内完成点单，在淘宝闪购内部看不到千问发的优惠券

这次活动的特点是：真金白银砸钱，门槛极低，微博上热搜，扩圈度高。

那为啥阿里要花钱砸千问呢？

  1. 千问抢的是「AI+生活消费」第一入口位
  2. 千问卖的不是模型，是使用路径
  3. 这次扩圈，顺带测试了一下千问点单路径能不能扛住极端高并发场景

与此同时，腾讯元宝则优惠平平，那是腾讯没钱吗？
不是，是因为元宝跟千问的定位不同。

千问需要扩圈，做用户生活里的智能生活操作系统（支付/履约/供给）。元宝则更像是嵌入到腾讯生态内的插件，它跟千问不同的点是，用户早就在腾讯生态内了，不需要花钱做活动扩圈。
腾讯不需要你想起元宝，只需要你在原有行为里顺带用一下。

所以元宝是防御性部署，千问是进攻型营销。

技术手记｜代码审核新思路

发表于 2026-02-09 11:42:30 更新于 2026-02-09 11:42:30 分类于 技术手记

SOP

写代码->本地跑最小门槛

  • formatter/lint/静态检查（能自动化就自动化）
  • 单测（至少新增/改动路径覆盖到）

Codex code-level review -> 产出报告到docs/codex-reviews

  • Codex只盯：可读性，明显bug，边界条件，并发/资源泄露，日志与异常处理，潜在的NPE，SQL/缓存误用，未处理的失败路径
  • 报告要可检索：按照日期+模块命名，例如：2026-02-08-login-token.md

我按照报告改 -> 再跑测试

  • 这一步配合一个「勾选清单」，避免改着改着把主线改丢

Thinking 做第二层 review（设计/上限风险/功能缺口）

  • 重点盯：接口契约，幂等性，降级，限流，可观测性，缓存一致性，事务边界，并发与重试策略，数据增长后的性能拐点，最容易上线炸的路径。

压测与文档收尾

  • 压测不是跑一下，而是：场景，数据规模，并发模型，指标口径，瓶颈定位，结论与改动建议
  • 文档：模块介绍/接口文档/关键设计决策（为什么这么做，不那么做）

这个设计的优点

  • 降低心里摩擦：不需要每次凭意志力信自己对还是错，而是把信任外包给流程，流程跑完，人就安心。
  • 可复盘，可证明：docs/codex-reviews + 压测文档，做成工程能力证据链
  • 把注意力分层：Codex抓底层bug（拼写，分支遗漏，NPE，资源关闭，日志），Thinking抓系统性炸点（幂等，重试风暴，缓存击穿，慢SQL，错误码契约）
  • 形成可重复的“模块闭环”：不是一直写，而是交付一个个完成的态的模块

主要风险点

  1. 文档负债风险
    • 如果每次review都提交一次review报告，很快会被文档淹死
    • 解决：只有以下情况固化到repo
      • 新模块完成
      • 关键重构
      • 性能优化前后
      • 上线前检查
    • 其他最小改动只留在PR描述或者临时notes
  2. 报告噪音与形式主义
    • Codex容易给一堆看起来很对但不关键的建议
    • 解决：让报告强制分级
      • P0:必须改，会上线炸
      • P1:应该改，影响可维护/性能
      • P2:可选优化
  3. 泄漏风险
    • 把review 文档提交到repo，容易不小心带上：内部url，token，真实数据样例，库表敏感字段。
    • 解决：报告模板里加一条规则：不得出现真实密钥/真实用户数据/完整链接串，样例一律脱敏
  4. 双review导致节奏变慢
    • 每个模块看起来更慢，但这算是返工减少的慢
    • 解决：
      • 对小改动走“轻量链路”：本地检查 -> 小范围Codex review（不落文档）-> 测试；
      • 只有交付级模块才走全链路

输出格式

docs/codex-reviews/报告模板

  • 变更摘要
  • Codex发现
    • P0：问题/影响/建议修改点（指到文件+函数）
    • P1: …
    • P2: …
  • 已经处理的清单（checkbox)
  • 遗留项（明确说明为什么不改+风险说明）

压测文档最小模板

  • 环境（机器，JVM参数，DB/Redis规格，版本）
  • 场景（接口，数据量，并发，持续时间，思考时间）
  • 指标（P50/P95/P99，吞吐，错误率，CPU/GC/DB慢查询）
  • 结论（瓶颈点&下一步优化路线）

自动化链路

  • PR自动跑：lint + test + 静态扫描（SpotBugs/Checkstyle/Semgrep之类）

前情回顾：
我的一个方法流程是：

  1. redis读写（业务状态）
  2. DB读写
  3. redis读写（缓存态）

我纠结的问题点：

  1. 目前情况会导致事务回滚DB数据，而redis数据没有同步回滚
  2. 考虑afterCommit，提交事务之后再读写redis，但因为流程不可拆，所以该方案不行。

我考虑的解决方案：

  1. 显示补偿，不是强一致。
  2. Canal

方案1如何操作：

该方案适合：

  1. 状态机
  2. 次数扣减
  3. workflow

方案2Canal

  1. 第一步redis，自己写
  2. 第三步redis，交给Canal

Canal能做的：

  1. 监听DB binlog
  2. DB commit之后，异步更新redis/es/mq

Canal解决的问题是：「DB -> Redis的单向同步」

Canal使用场景：

  1. 多表多服务共享redis
  2. 读多写少
  3. 强烈不想在业务代码里碰缓存
  4. 接受秒级延迟
  5. 有运维精力

另，redis的状态如何区分？

  • 业务态Redis（不需要强一致，出问题靠TTL/补偿，不需要进事务）
    • 限流
    • 去重
    • 幂等
    • 状态机 step
    • 分布式锁
  • 缓存态Redis（DB派生）（严格afterCommit，删除缓存/重建）
    • 详情缓存
    • 聚合结果

技术手记｜实体类设置默认参数值的注意事项

发表于 2026-02-08 21:12:21 更新于 2026-02-08 21:12:21 分类于 技术手记

实体类加注解注意事项

  1. 数据库是最终兜底，实体类是前置判断
  2. 最简单直观的方式是：直接给默认值，类似：private Integer status = 1
  3. 构造方法里默认赋值：风险：如果全参构造/Builder，容易被覆盖，不如直接初始化字段稳定
  1. JPA/ Hibernate注解（只对JPA有效，对MyBatis没用）

这个只在

  • Hibernate自动建表或者生成DDL才有用，new User()的时候，status还是null

这个只在save()前兜底一次，MyBatis用不了

  1. Mybatis需要特别注意的坑点：

如果status = null，实际执行的是：status = null，DB默认不会生效，直接报错。
解决办法，用动态SQL

技术手记｜我写加密工具类，又踩新坑，把pepper当message传入了

发表于 2026-02-08 20:15:05 更新于 2026-02-08 20:15:05 分类于 技术手记

错误版本：SHA256(input + pepper)

这个版本错误有二：

  1. input + pepper在密码学上是自制协议，有长度拓展，歧义风险
  2. 语义不清：pepper是密钥，不能当成message的一部分

正确版本：HMAC(key = pepper, message = input)，在Java里就是HmacSHA256

另，其他bug：

  1. @Autowire不能注入static
  2. new Security()会绕过Spring，可以改为构造器注入

这种写法的使用场景：

  1. 登录校验
  2. token派生（服务端不可伪造token）
  3. 签名校验
  4. 内部安全字段

技术手记｜改createUser存在性校验挡不住并发重复注册怎么改？

发表于 2026-02-06 21:34:07 更新于 2026-02-06 21:34:07 分类于 技术手记

改之前的流程：

  1. 构造user
  2. 通过phone和userId查user是否存在，存在throw ErrorCode
  3. 插入user

改之前的问题：

  1. userId是刚生成的，不会重复
  2. 真正重复的只有phone
  3. 并发场景下：
    • 两个请求同时查询
    • 都查询不到
    • 都insert
    • 都注册【重复注册】

所以这种「先查再插」在并发下必挂。

改后思路：

  1. user.phone唯一索引【已有】
  2. createUser不做exists查询
  3. 直接insert，靠捕获DuplicateKeyException防并发

改完之后的思维模型是：

  1. 参数校验
  2. 构造user
  3. 直接insert user
    • 成功：继续
    • DuplicateKeyException: 查已有user，直接用
  4. 确保 role 存在（insert + 忽略重复）
  5. 确保 userRole 存在（insert + 忽略重复）
  6. return user

另，存在性校验是干嘛的？

存在性校验不是业务逻辑，而是数据完整性

而且必须由DB唯一约束兜底。

技术手记｜redis和事务的雷我又踩上了（笑）

发表于 2026-02-05 19:43:51 更新于 2026-02-05 19:43:51 分类于 技术手记

如题。
我代码的逻辑是：

  1. redis（读写）
  2. DB读写（封装了private方法）
  3. redis（读写）

这涉及两个问题：

  1. private方法加事务，无效，因为Spring事务是走AOP的，但AOP不拦截private方法。就算加了@Transactional注解，也不会拦截。
  2. redis + DB事务，DB回滚，但redis没有回滚，导致数据不一致。

问题一改法：

  1. 把事务加到调用private方法的public方法
  2. 使用AspectJ，绕过Spring AOP的public限制

问题二改法：

  1. 使用afterCommit，在提交事务之后再更新redis的值
