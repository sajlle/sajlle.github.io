技术手记｜改createUser存在性校验挡不住并发重复注册怎么改？

发表于 2026-02-06 21:34:07 更新于 2026-02-06 21:34:07 分类于 技术手记

改之前的流程：

  1. 构造user
  2. 通过phone和userId查user是否存在，存在throw ErrorCode
  3. 插入user

改之前的问题：

  1. userId是刚生成的，不会重复
  2. 真正重复的只有phone
  3. 并发场景下：
    • 两个请求同时查询
    • 都查询不到
    • 都insert
    • 都注册【重复注册】

所以这种「先查再插」在并发下必挂。

改后思路：

  1. user.phone唯一索引【已有】
  2. createUser不做exists查询
  3. 直接insert，靠捕获DuplicateKeyException防并发

改完之后的思维模型是：

  1. 参数校验
  2. 构造user
  3. 直接insert user
    • 成功：继续
    • DuplicateKeyException: 查已有user，直接用
  4. 确保 role 存在（insert + 忽略重复）
  5. 确保 userRole 存在（insert + 忽略重复）
  6. return user

另，存在性校验是干嘛的？

存在性校验不是业务逻辑，而是数据完整性

而且必须由DB唯一约束兜底。

这涉及两个问题：

问题一改法：

  1. 把事务加到调用private方法的public方法
  2. 使用AspectJ，绕过Spring AOP的public限制

问题二改法：

  1. 使用afterCommit，在提交事务之后再更新redis的值

让Codex帮我审代码 ｜ Codex帮我填平了404/击穿/缓存被删的坑

发表于 2026-01-09 18:52:00 更新于 2026-01-09 18:52:00 分类于 技术手记

Codex帮我改了几个地方，我复盘如下：

lockKey的前缀从CACHE_KEY_PREFIX改成LOCK_KEY_PREFIX

改了之后，缓存和锁物理上隔离：

  • 缓存Key：cache:shop:{id}存真实JSON
  • 锁Key：lock:shop:{id}存锁占用标记
    这属于缓存并发的底层卫生，锁是锁，缓存是缓存。

不改会导致：

  • 一个key既当缓存，又当锁。

会同时引发三类事故：

  • 缓存存在时，永远拿不到锁 –> 逻辑分支直接走歪
    • SETNX(cache:shop:1, "1")在缓存已经存在时会失败
    • 永远进不去回源DB的分支，shop可能一直是null，后续很容易触发写空值缓存/返回null的逻辑。造成明明有店铺却返回不存在（假404）
  • 缓存不存在时，锁把缓存Key写成"1"，下一次读缓存会读到垃圾

一次把缓存当锁用的事故：Shop 查询接口击穿/误删/假404复盘

发表于 2026-01-09 18:46:02 更新于 2026-01-09 18:46:02 分类于 技术手记

一次把缓存当锁用的事故：Shop 查询接口击穿/误删/假404复盘

我在 Shop 查询接口里实现了缓存击穿保护，结果把缓存当锁用了：解锁时顺手把缓存删了。压测一跑，DB 像被踹了一脚，抖得很有节奏。

0. 背景：Day2 验收目标是什么？

  • 目标接口：GET /shops/{shopId}
  • 验收：
    1. 店铺不存在：返回错误码，且不打爆 DB（空值缓存）
    2. 热点店铺：并发下不打爆 DB（互斥/逻辑过期）

1. 现象：问题怎么暴露的？

  • 并发压测时 DB 回源次数异常

2. 根因：到底哪里写错了？（按严重级别）

2.1 Critical：锁 key 与缓存 key 混用

  • 现象：unlock 可能误删缓存，导致缓存抖动
  • 后果：热点击穿 → DB 抖动
  • 修复：lockKey 与 cacheKey 分前缀

2.2 Critical：并发 miss 抢不到锁却写空值缓存（假404）

  • 现象：真实有数据却被缓存为空
  • 后果：长时间错误 404
  • 修复：拿不到锁就 sleep + 重读缓存，不写任何缓存

2.3 Medium：lon/lat 未判空导致 NPE

  • 现象：不传定位参数直接 500
  • 修复：lon/lat 与 shop 坐标双向判空

2.4 Low：type 判空缺失导致 NPE / 错误码不清晰

  • 修复：type 为空返回明确错误码

注：如果你的入口实际是 ShopServiceImpl#getById，还需要补齐 shopId/status/typeName/空值缓存等校验。

3. 最小补丁：改动点（只贴关键 diff）

    1. lockKey 前缀修正
    1. tryLock 失败的处理：sleep + 重读缓存
    1. miss 回源后写入逻辑过期缓存 / 空值缓存
    1. lon/lat 判空

4. 回归测试：怎么证明真的修好了？

4.1 不存在店铺：防穿透

  • 删除缓存 key
  • 并发请求不存在 shopId
  • 预期：DB 只回源一次（或极少），后续命中空值缓存

4.2 热点店铺：防击穿

  • 删除缓存 key
  • “瞬间并发”请求同一 shopId（不要慢爬升）
  • 预期：DB 回源次数≈1，其余等待锁或读缓存

4.3 lon/lat 缺省

  • 只传 shopId
  • 预期：200，distance 为空

5. 沉淀：Shop 查询接口容错点清单（可复用）

  • 容错点01：锁 key 与缓存 key 必须隔离
  • 容错点02：抢不到锁禁止写空值缓存
  • 容错点03：逻辑过期必须保证首次建缓存
  • 容错点04：经纬度可选参数要双向判空
  • 容错点05：type 可能脏数据要判空
  • 容错点06：status 校验必须在缓存层/业务层明确

unlock()无条件delete——会误删别人的锁

比如：

在分布式里会出现经典事故：

  1. 线程A抢到锁（10秒过期）
  2. A业务执行慢（比如查库慢，GC，断点调试），超过10秒
  3. 锁过期
  4. 线程B抢到同一个锁key
  5. A执行完，finally里delete(lockKey)，把B的锁删了。
  6. 线程C又抢到锁，于是B和C同时重建缓存/同时写数据库

这就是为啥分布式锁一定要有「锁拥有者标志（token）」，解锁必须校验。

tryLock缺乏token（唯一标志）

比如：

这样不知道锁是不是自己加的，所以解锁时没法校验，只能盲删——于是必然有误删除的风险。

锁过期不续期——别人抢锁，误删别人的锁

如果不做watch dog，而`LOCK_EXPIRE < 最坏情况下的缓存重建时间（查库 + 序列化 + 写Redis + 抖动）

那么会出现：

锁过期 –> 别人抢到 –> 误删别人锁

如何改？

思路很简单：加token + Lua脚本原子校验删除

  • tryLock：value存一个随机token（比如UUID）
  • unlock：只有当Redis里value == 我当初的token才delete
    • 这一步必须原子（Lua），否则也会有竞态

要不要加watch dog？

  • 一般不要，因为缓存重建通常很快（几十毫秒～几百毫秒），但如果有
    • 慢SQL（秒级）
    • 网络抖动
    • 调试时打断点
      那锁过期就会频繁发生，工程上：要么把锁TTL拉长，要么做watch dog

try catch为啥要写到锁外面？

发表于 2026-01-05 15:58:45 更新于 2026-01-05 15:58:45 分类于 技术手记

简略答案：

try/catch准确来说是try/finally要把可能提前return/抛异常的整段流程罩住，才能保证只要拿到锁，就一定会释放锁。

锁的场景里，真正需要的是try/finally

锁的场景里，最关键的是：

  • 代码途中return
  • JSON解析/查库/Redis任何一步抛异常
  • 甚至自己写错导致NPE

都不能让人把锁带走，否则就死锁（分布式锁就是锁key一直挂着直到过期）

所以标准结构是：

finally是兜底：return 也会执行finally

为什么try要写在锁外面那层，而不是塞进locked分支？

如果把try写进if(locked){...}里，会发生什么？

问题A：你会很难保证所有路径都释放锁

代码很多return

  • 命中缓存return
  • double-check 命中 return
  • 查库后 return

如果try/finally只包住locked分支内部，一旦在外面某条路径return，就得自己记得释放锁。但人很容易忘记。

把try/finally放到外层：怎么return都跑不掉finally

问题B：你会被迫写多份儿try结构（长/乱/易错）

锁逻辑一般是：

  • 没拿到锁：sleep + retry
  • 拿到锁：double-check + rebuild
    这两段都可能抛异常，都可能return

如果try只写在locked分支里，那没拿到锁的分支要不要try？也要。

结果：要复制一堆try/catch/finally，代码更长，bug概率更高。

外层一个try/finally，把所有分支统一罩住最省心。

问题C：异常不只会发生在锁内部

很多异常点其实发生在locked之外，比如：

  • Thread.sleep(...)抛InterruptedException（通常在没有拿到锁那条分支）
  • 在else分支里重试读缓存，解析JSON
  • 甚至unlock本身，也可能出问题（例如 Redis 短暂不可用）

所以try放外面是为了：所有路径异常都能被统一处理

锁代码骨架模板

总结

  1. try/finally一定包住所有return的地方
  2. unlock只放finally
  3. 只有locked == true才unlock

空值缓存可以防止缓存穿透，但……什么时候要用它呢？

发表于 2026-01-05 15:41:52 更新于 2026-01-05 15:41:52 分类于 技术手记

场景：

我写店铺列表接口，要不要上空值缓存呢？
key是固定的cache:shop:types

列表接口缓存空值，到底在防啥？

因为我们这边的key是固定的，所以不大可能会出现“不同id被人恶意传参穿透“的情况。

但它会遇到两种现实的问题：

场景1：数据真的为空（初始化/测试库/被误删/迁移期间）

比如：

  • 新环境刚起，shop_type表还没有导入
  • 测试库就是空的
  • 生产迁移时短暂空窗
  • 有人误删了类型表数据

这时候你如果不缓存空列表，会发生什么？

  • 每一个请求都会miss（因为你不写缓存）
  • 每一个请求都会去查DB
  • DB这条SQL会被持续刷屏
    这叫“空结果击穿/持续回源”（不算经典穿透，但效果类似：一直打库）

缓存空值，就能让系统在“确定为空”期间：

  • 只打库一次
  • 后续请求都直接返回空列表
  • 等数据补上之后（或者删除缓存），再恢复正常

    这在“配置/字典类数据”上很常见，你要允许系统在异常数据态下仍然稳定。

场景2：DB/Mapper间歇性返回空（抖动/超时降级/读写分离延迟）

有些情况会被认为「查不到就是空」，但可能是：

  • 读库刚切换，延迟，短暂不可用
  • 超时会被熔断/降级处理成空集合
  • SQL会被限流，返回空（取决于代理/中间件）
  • catch了异常，错误地返回Collections.emptyList()

如果这类偶发空，经常发生，而空值缓存TTL设置的很长，就会把偶发故障固化。

所以正确的姿势是：

  • 空值缓存也可以做，但TTL要够短（分钟级）
  • 让它只是短暂回血，而不是长期误导

那店铺列表真的需要空值缓存吗？

看业务约束。

如果你认为“店铺列表类型不可能为空，空就是故障”，那你可以：

  • 不缓存空值
  • 直接抛异常/返回错误码
  • 同时报警

如果你希望“就算为空也别把DB打爆，系统先稳住“，那就：

  • 缓存空列表，TTL分钟级（2～10分钟）
  • 并且在后台日志里标记，店铺列表为空，供后续排查

总结

  • 查询详情：防 穿透（不存在的id反复被查询）
  • 查询列表：防 空结果持续回源（确实为空的时候反复被查）+ 防止故障抖动导致反复重建/打库
