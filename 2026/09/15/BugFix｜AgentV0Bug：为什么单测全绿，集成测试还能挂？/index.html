BugFix｜AgentV0Bug：为什么单测全绿，集成测试还能挂？

发表于 2026-09-15 18:57:26 更新于 2026-09-15 18:57:26 分类于 BugFix

Bug回顾

测试AgentV0的时候出现了一个Bug，也就是RefundCaseExplanationControllerIT 稳定5/5 context startup error: No qualifying bean of type ExplanationPromptFactory。单独运行同样失败，所以这不是flaky。

这个bug检查的思路是：先判断是production application wiring本身缺bean，还是refundCaseExplanationControllerIT的TestConfiguration/imports已经落后于最近的多SDK重构。
不先预设是测试问题。

给Codex的指令

然后我找Codex排查，要求它：

  1. 先追踪完整依赖链条，读取完整的Spring context failure，明确constructor 依赖哪个bean，最终要求explanationPromptFactory，为什么当前的ApplicationContext没有注册它。先汇报实际的dependency chain，不先改代码。

  2. 验证production context，分别验证两个Case。CaseA-AI disabled，在没有真实API key，AI disabled 的配置下，应用context必须正常启动。 CaseB-AI enabled/fake provider environment。使用测试配置或者fake provider，不调用真实互联网。如果explanation功能开启，则所有的production-required bean必须完整存在。确认当前真实调用链能成功装配。如果production-environment context本身也缺bean，这是production wiring defect。不要只修测试。

  3. 如果仅TestConfiguration缺乏bean，也就是production context正常，但是refundCaseExplanationControllerIT因为自己的@Import/@TestConfiguration替换provider之后漏掉了deterministic prompt factory，则只修装配测试。优先注册真实的explanationPromptFactory，因为prompt factory是纯确定性组件，没必要mock。不许为了让context绿了儿把

    • production dependency改成optional
    • 使用@Autowired(required=false)
    • 给整个application 加宽泛的component scan
    • mock掉RefundCaseExplanationService
    • mock掉deterministic diagnosis chain
      且该IT仍然保持：
    • HTTP
      • real controller
      • real explanation service
      • real deterministic core
      • fake provider/network boundary

  4. 如果production wiring真的缺乏bean，也就是production-equivalent context也无法启动，那就修最小production configuration。要求是：

    • 一个且只有一个明确的ExplanationPromptFactory Bean
    • 多provider多情况下不要产生ambiguous beans
    • provider-specific配置不要泄漏到deterministic core
    • AI disabled时，deterministic /diagnosis 仍能启动
    • 不通过optional dependency掩盖配置错误

  5. 增加wiring regression test
    至少保证：

    • AI disabled: application context starts & /diagnosis available
    • Explanation test configuration: application context starts && ExplanationPromptFactory bean resolvable && /explain pipeline callable with fake provider
    • 不存在：NoSuchBeanDefinitionException && NoUniqueBeanDefinitionException

  6. 不许扩大本轮次范围，不许改：Facts, Diagnosis, Decision, AllowedAction, Playbook, finish reason白名单，strict coercion rules, CaseExplanation schema, provider retry/timeout, AgentLoop/Tool Calling/ RAG/ Memory，而且不许调用真实的付费API

  7. 验证：
    先执行：

    • RefundCaseExplanationControllerIT
    • explanation/ provider相关targeted tests
    • strict Gateway tests
      然后在确认可信的非File Provider隔离目录执行两次mvn clean verify，两次之间不得修改文件

  8. 最终报告：需要汇报

  • 缺乏Bean的完整dependency chain
  • 根因属于 production wiring 还是test wiring
  • 为什么之前转向的Gateway测试没有发现
  • 最终修改文件
  • AI disabled context测试结果
  • fake-provider explanation context结果
  • RefundCaseExplanationControllerIT结果
  • strict Gateway test是否全绿
  • 两次mvn clean verify的结果
  • 本轮diff和既有的working tree diff的边界
  • 推荐commit message

Codex的回复摘要

根因是RefundCaseExplanationControllerIT测试装配落后于多SDK重构，不是production wiring缺陷。

  1. 缺Bean的完整依赖链条：

Optional<LlmReasoner>不能兜底，因为候选LlmReasoner已经存在，只是在创建过程中缺乏依赖。

  1. 根因属于test wiring，生产入口扫描能够发现LlmCommonConfiguration，后者无条件注册唯一，provider-neutral的ExplanationPromptFactory。IT使用手写的@Import，却只引入了OpenAiLlmConfiguration，漏掉了公共配置。
  2. 专项Gateway测试没有发现，是因为：
    • Gateway直接构造单测对象，不启动Controller IT上下文
    • provider selection测试已经显式引入LlmCommonConfiguration
    • 普通的mvn test不执行Failsafe的*IT
  3. 最后只修改了RefundCaseExplanationControllerIT
    • 导入了LlmCommonConfiguration
    • 在测试应用的@Import中注册该真实配置

Bug复盘

此次Bug可以概括成：

多Provider重构之后，生产环境通过package scanning 能拿到公共 PromptFactory，但集成测试为了控制provider使用手写@Import，漏掉了provider-neutral公共配置，单测因为直接构造了Gateway全绿，直到Failsafe Controller IT才暴露。最终没有修改生产wiring，只让测试装配重新对齐真实的application context。

正好可以回答标题：为啥单测全绿，集成测试还能挂？答案是：「单测验证的是对象行为；这次坏的是Spring application wiring」
也就是说：「Spring测试上下文和生产上下文并不天然等价。

那为啥Optional<LlmReasoner>没有防止测试失败？

毕竟我们写了Optional<LlmReasoner>直觉可能觉得「没有LLM Bean，那就Optional.empty()，为啥还启动失败？」
因为这里不是「容器里根本没有LlmReasoner候选」，而是：「容器发现了openAiLlmReasoner，开始创建它，创建的时候发现ExplanationPromptFactory不存在，Bean创建失败」。而Optional<T>能处理的是：「0个T -> Optional.empty()」，处理不了「有一个T是候选，但这个T是坏的，创建失败」。

所以Optional<LlmReasoner> reasoner不是不管LlmReasoner内部炸成什么样都算empty，而是如果没有注册LlmReasoner，可以接受。

那为什么Gateway单测全绿，直到ControllerIT才炸？

因为测试层级不同。

Gateway单测，大概类似，new SdkCompatChatGateway(...)，对象直接new。它能验证：

  • JSON parsing
  • strict schema
  • finish reason
  • coercion
  • malformed response
    但它根本没问Spring，你能不能把整条/explain依赖装配起来。所以看不到bean丢失。

那为啥Provider selection test绿了呢？

因为这类测试已经显式的import LlmCommonConfiguration，所以它也是绿的。

为啥普通的mvn test也绿呢？

因为普通的mvn test的时候，Failsafe的*IT不执行。所以单元测试全绿。并不代表整个Spring HTTP integration context能启动。
直到mvn verify跑到RefundCaseExplanationControllerIT，才第一次真正走了

所以炸出来了。
